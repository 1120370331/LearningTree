# 测试设计与调试定位

## 学完要能做到什么

能从失败现象建立可复现案例，选择合适的测试层级，并用可观察行为而非内部实现作为断言。

## 核心概念

调试先描述具体输入、步骤、预期与实际结果，再缩小问题边界。Console、Network、断点和调用栈分别提供不同证据；随意同时修改多个位置容易掩盖真正原因。

纯计算适合单元测试，组件交互适合通过可访问角色与文字操作，关键跨系统流程适合少量端到端路径。测试层级由风险与真实边界决定，不是越大越好，也不是全靠 mock 就能证明数据库或网络集成。

好的断言描述用户可观察结果或稳定契约。等待异步条件优于固定睡眠；隔离数据和可控时钟有助于减少偶发失败。修复应针对已证实原因，回归测试保护有价值的失败模式。

## 读懂一个最小例子

```javascript
const result = total([{ price: 10, count: 2 }, { price: 5, count: 1 }]);
expect(result).toBe(25);
// 组件测试中：点击“保存”，等待“已保存”或明确的错误反馈。
```

金额函数用明确输入输出验证；界面则观察点击后的结果。不要只断言内部函数被调用，就假定保存与持久化一定成功。

## 两个容易混淆的地方

- 调用记录不能证明真实持久化与恢复结果，需要覆盖相关边界。
- 用户点击完成并不总意味着所有异步业务已结束。

## 动手完成一个小作品

为“刷新后任务消失”写一份缺陷定位记录和最小回归方案。

完成后，用下面的标准观察实际产出，而不是只看代码是否写完：

- 预期与实际及输入可复现
- 区分界面、API、数据库和恢复环节
- 回归方案保护实际丢失问题而非仅检查函数调用

## 如何留下学习证据

先完成本节练习，再在底部开始测验。选择、填空、排序与代码阅读自动判分；简答、改错和实战需要你对照参考答案逐项自评。自评不会计入自动正确率，也不代表系统已经执行或审查你的代码。

把仍说不清的概念写进个人笔记。复习时先尝试回答“为什么按钮保存成功的组件测试仍不能单独证明 SQLite 持久化正确？”，再核对参考解释。
