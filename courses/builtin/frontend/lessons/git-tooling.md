# Git、依赖与可复现构建

## 学完要能做到什么

能区分工作区、暂存区与提交，使用锁文件重建依赖，并保持配置、秘密和构建产物的清晰边界。

## 核心概念

Git 的工作区是正在编辑的文件，暂存区决定下一次提交包含哪些内容，提交记录一个快照。提交前应看清 diff，避免把本地数据或无关改动一起带入；分支有助于隔离任务，但不会替你判断改动是否属于当前需求。

package.json 描述依赖范围和项目脚本，锁文件记录解析结果。npm ci 面向已有且一致的锁文件安装，会重建 node_modules；不要把它和随意更新版本混在一起。运行时版本、锁文件、配置和构建命令共同影响可复现性。

前端打包器会把可访问的客户端配置编入产物，环境变量名带有“secret”也不能阻止泄露。秘密必须保留在服务端。dist、node_modules 和本地数据库通常按项目约定忽略；示例配置应保留字段说明但不含真实凭证。

## 读懂一个最小例子

```text
git status
git diff
git add src/CourseCard.tsx
git diff --cached
git commit -m "修复课程卡片名称"
```

先看改动，再精确暂存，最后确认暂存内容形成的提交。这里的路径与说明是示例，实际提交范围应与任务一致。

## 两个容易混淆的地方

- 客户端产物和请求可被查看，秘密应保留在服务端。
- 只改环境变量名称不能保护会被打包进浏览器的秘密。

## 动手完成一个小作品

为一个前端项目写可复现交付说明，并整理一次只含目标改动的提交。

完成后，用下面的标准观察实际产出，而不是只看代码是否写完：

- 其他人可按说明恢复环境
- 锁文件与依赖定义一起维护
- 提交范围明确且不含秘密或本地数据

## 如何留下学习证据

先完成本节练习，再在底部开始测验。选择、填空、排序与代码阅读自动判分；简答、改错和实战需要你对照参考答案逐项自评。自评不会计入自动正确率，也不代表系统已经执行或审查你的代码。

把仍说不清的概念写进个人笔记。复习时先尝试回答“为什么只写“npm install 后能跑”不足以描述可复现交付？”，再核对参考解释。
