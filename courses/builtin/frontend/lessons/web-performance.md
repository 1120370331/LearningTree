# 性能、加载与测量

## 学完要能做到什么

能区分加载、响应与布局稳定性，用测量定位瓶颈，并解释资源优化和交互优化的适用范围。

## 核心概念

Core Web Vitals 用 LCP 描述主要内容加载体验，INP 描述交互响应，CLS 描述意外布局偏移。真实用户数据与实验室数据用途不同；单次本机快并不代表所有设备与网络都快。

图片尺寸、格式、优先级与缓存会影响加载。提前为图片保留比例可减少布局跳动；首屏关键图不宜盲目懒加载。代码拆分减少初始下载，但拆分粒度和请求瀑布也需要权衡。

长任务会占据主线程，拖慢输入响应。先定位昂贵计算或渲染，再考虑分片、减少工作量、虚拟列表或 Worker。仅减小图片无法解决所有脚本卡顿，优化应有同条件前后证据。

## 读懂一个最小例子

```html
<img
  src="course-cover.webp"
  width="800" height="450"
  alt="课程章节示意"
  style="max-width:100%;height:auto"
>
```

明确宽高比例让浏览器在图片下载前保留空间。它有助于布局稳定，但不自动保证图片字节小或首屏加载快。

## 两个容易混淆的地方

- 真实设备、网络和使用路径不同，应结合真实用户数据与可复现测量。
- 预留几何空间解决布局跳动；压缩字节解决的是另一类加载问题。

## 动手完成一个小作品

为一个含封面和长列表的页面写性能改进记录，只选择一个已定位瓶颈实施改动。

完成后，用下面的标准观察实际产出，而不是只看代码是否写完：

- 场景和基线可复现
- 改动直接对应已定位瓶颈
- 结果比较包含限制与副作用而非只报一个分数

## 如何留下学习证据

先完成本节练习，再在底部开始测验。选择、填空、排序与代码阅读自动判分；简答、改错和实战需要你对照参考答案逐项自评。自评不会计入自动正确率，也不代表系统已经执行或审查你的代码。

把仍说不清的概念写进个人笔记。复习时先尝试回答“为什么不能把所有图片都设 loading="lazy" 当成通用性能方案？”，再核对参考解释。
