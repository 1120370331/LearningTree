# 可访问性与交付质量

## 学完要能做到什么

能通过键盘、名称和反馈建立完整操作路径，处理焦点管理，并理解自动检查的覆盖边界。

## 核心概念

可访问性首先依赖清晰语义、可操作控件与合理阅读顺序。可访问名称告诉用户控件做什么；图标按钮需要明确名称，装饰图不应重复制造噪声。优先使用原生元素，ARIA 用于补足实际缺失的信息。

键盘操作需要可见焦点和合理顺序。对话框打开后应把焦点放到适当位置、限制在模态内容内，关闭后回到触发位置；Escape 行为要符合组件预期。仅加 role=dialog 不会自动实现全部行为。

错误与成功不能只靠颜色表达。动态重要反馈可通过适合的 live region 提示，但避免不断播报造成干扰。自动工具能发现部分问题，键盘路径、读屏语义和内容理解仍需要实际观察。

## 读懂一个最小例子

```html
<button type="button" aria-label="删除这条笔记">
  <svg aria-hidden="true" focusable="false" viewBox="0 0 24 24"><path d="M6 6h12v14H6z"/></svg>
</button>
<p role="status">笔记已保存</p>
```

按钮拥有明确名称，装饰图标不重复朗读。status 适合温和提示状态变化；不要把每次输入都当成需要抢占注意的警报。

## 两个容易混淆的地方

- 自动工具只覆盖部分可检测规则，真实交互仍需观察。
- 符号外观不保证用户理解操作，也不提供完整键盘行为。

## 动手完成一个小作品

为学习应用的“打开笔记 → 编辑 → 保存 → 关闭”设计一条完整键盘路径，并改进错误反馈。

完成后，用下面的标准观察实际产出，而不是只看代码是否写完：

- 全部主要操作可用键盘完成
- 焦点管理和名称清楚
- 成功错误可感知且失败不丢输入

## 如何留下学习证据

先完成本节练习，再在底部开始测验。选择、填空、排序与代码阅读自动判分；简答、改错和实战需要你对照参考答案逐项自评。自评不会计入自动正确率，也不代表系统已经执行或审查你的代码。

把仍说不清的概念写进个人笔记。复习时先尝试回答“为什么给 div 加 role="button" 仍不足以获得完整按钮体验？”，再核对参考解释。
